راه‌اندازی (Render):
۱. مخزن گیت‌هاب بساز، این پوشه را در آن آپلود کن (index.html باید داخل public بماند).
۲. در render.com: New -> Blueprint -> همان مخزن را انتخاب کن (render.yaml خودش سرور و دیسک دائمی را می‌سازد).
۳. این متغیرها را در Render وارد کن:

BOT_TOKEN     = توکن ربات تلگرام
ADMIN_IDS     = آیدی عددی تلگرام خودت (با کاما اگر چند نفر)
RATE_URL      = http://api.navasan.tech/latest/?api_key=YOUR_KEY&item=usd_sell
RATE_PATH     = usd_sell.value
RATE_SEC      = 10   (فقط اگر پلن پولی نوسان داری؛ با پلن رایگان هر ۲ ساعت یک‌بار بروز می‌شود پس این عدد را روی 1800 بگذار)

نرخ دلار (منبع واقعی):
نوسان (Navasan) یکی از قدیمی‌ترین و معروف‌ترین وب‌سرویس‌های نرخ ارز ایران است.
کلید رایگان: ربات تلگرام @navasan_contact_bot پیام بده، کلید ۱۲۰ درخواست ماهانه رایگان می‌دهد
  اما با پلن رایگان نرخ فقط هر ۲ ساعت بروز می‌شود، نه لحظه‌ای.
برای واقعاً لحظه‌ای شدن (هر چند ثانیه) باید پلن "استاندارد" یا "طلایی" را از همان سایت بخری
  (navasan.tech/api -> پلن‌ها، پرداخت با تتر). راهنمای کامل: navasan.tech/api/webserviceguide

قیمت دلاری هر استارز تلگرام:
تلگرام و Fragment.com (بازار رسمی خودِ تلگرام) API عمومی برای این عدد منتشر نکرده‌اند؛ یعنی
هیچ منبع رسمی، لحظه‌ای و رایگانی برای گرفتن خودکار این رقم وجود ندارد. عدد رایج بازار همین
الان چیزی حدود ۰.۰۱۳ تا ۰.۰۱۵ دلار به ازای هر استارز است (روی Fragment.com قابل چک کردن دستی).
به همین دلیل این عدد در پنل ادمین دستی تنظیم می‌شود (star_usd) و باید هر چند وقت خودت
با نگاه به Fragment.com به‌روزش کنی. اگر بعداً منبع رسمی و لحظه‌ای پیدا شد، به‌راحتی می‌توان
همان الگوی RATE_URL/RATE_PATH را برایش هم اضافه کرد.

قیمت استارز به دلار — حالا واقعاً می‌تواند خودکار و رسمی باشد:
خودِ تلگرام یک پارامتر رسمی داخلی دارد به اسم stars_usd_sell_rate_x1000 که دقیقاً
"چند دلار برای هر ۱۰۰۰ استارز" را نگه می‌دارد (مرجع رسمی: core.telegram.org/api/config).
مشکل: این پارامتر فقط از طریق پروتکل MTProto (نه Bot API ساده‌ای که تا اینجا استفاده کردیم)
در دسترس است، یعنی باید با یک حساب کاربری واقعی تلگرام (نه ربات) به آن وصل شد.

راه‌اندازی (یک‌بار، روی کامپیوتر خودت، نه روی Render/Railway):
۱. برو my.telegram.org -> API development tools و یک api_id و api_hash بگیر.
۲. در پوشه پروژه: npm install
۳. اجرا کن: npm run get-session
۴. با شماره تلگرام خودت لاگین کن (کدی که تلگرام برایت می‌فرستد را وارد کن).
۵. سه مقدار TG_API_ID و TG_API_HASH و TG_SESSION چاپ می‌شود؛ این سه را در Render/Railway
   به‌عنوان متغیر محیطی اضافه کن.

بعد از این، سرور هر ۱۰ دقیقه خودش این نرخ را از تلگرام می‌گیرد و در پنل ادمین
کنار قیمت استارز می‌نویسد "منبع: خودکار از خود تلگرام". اگر این متغیرها را نگذاری،
دقیقاً مثل قبل، عدد را خودت دستی وارد می‌کنی — هیچ‌چیز نمی‌شکند.

هشدار صادقانه: من این بخش را تست زنده نکرده‌ام (چون به اینترنت وصل نیستم). کد بر اساس
مستندات رسمی تلگرام نوشته شده و دامنه‌ی معقول (۰.۲٪ تا ۵٪ دلار) را چک می‌کند تا اگر
عدد عجیب برگشت، جایگزین قیمت دستی‌ات نشود؛ ولی اولین بار که دیپلوی کردی، حتماً لاگ سرور
را نگاه کن و ببین خط "stars_usd updated from Telegram config: ..." را می‌بینی یا نه.

--- سخت‌گیری‌های امنیتی/عملیاتی اضافه‌شده (این نوبت) ---
- رفع کامل Stored XSS: هر متنی که کاربر یا ادمین وارد کرده (پیام، گیرنده، یادداشت، دلیل رد، یوزرنیم) قبل از
  نمایش Escape می‌شود؛ خطرناک‌ترین نقطه (پیام سفارش در پنل ادمین) که هیچ محدودیتی نداشت، همین‌جا بسته شد.
- DEV دیگر با یک متغیر به تنهایی روشن نمی‌شود: باید هم DEV=1 و هم ALLOW_DEV=1 باشد، وگرنه سرور اصلاً بالا نمی‌آید.
  هیچ‌وقت این دو را روی Render/Railway واقعی نگذار.
- هدر x-dev فقط وقتی از فرانت ارسال می‌شود که اصلاً داخل تلگرام باز نشده باشد (یعنی حالت تست بیرون از اپ).
- Security headers واقعی (CSP هماهنگ با Telegram WebApp، X-Content-Type-Options، Referrer-Policy، Permissions-Policy).
- Foreign Key و Index روی همه جدول‌های اصلی (users/orders/order_items/cart/topups/ledger).
- خطاهای برنامه‌ریزی‌نشده (باگ) دیگر پیام داخلی سرور را به کاربر نشان نمی‌دهند؛ فقط یک کد پیگیری (ERR-xxxx)
  می‌بینند و جزئیات کامل فقط در لاگ سرور می‌ماند. خطاهای شناخته‌شده (موجودی کم، تعداد نامعتبر و ...) کد HTTP درست
  خودشان را می‌گیرند (400/401/403/404/409/429/503).
- endpoint های /live و /ready برای مانیتورینگ.
- endpoint جدید /api/wallet/statement — کاربر تاریخچه کامل تراکنش‌های کیف پولش را می‌بیند (دکمه «تاریخچه کامل
  تراکنش‌ها» در تب کیف پول).
- endpoint جدید /api/admin/reconcile — چک می‌کند موجودی هر کاربر با آخرین رکورد لجر یکی باشد یا نه.
- Graceful shutdown: موقع ری‌استارت روی Render/Railway، سرور منتظر می‌ماند اتصال دیتابیس درست بسته شود.

--- چیزهایی که در این لیست بزرگ (۵۰ موردی) واقعاً نیاز به یک پروژه جدا دارند و اینجا حل نشدند ---
این‌ها را صادقانه می‌گویم چون تظاهر به حل‌شدنشان خطرناک‌تر از نگفتنشان است:
- RBAC چندسطحی (Super/Finance/Support Admin) — الان فقط یک سطح "ادمین" وجود دارد.
- Inventory Reservation واقعی برای گیفت‌ها — چون خودِ موجودی گیفت دست تلگرام است نه دیتابیس ما، رزرو واقعی
  فقط با API رسمی خرید گیفت از طرف ربات ممکن است که چنین APIای برای "ارسال گیفت از طرف ربات" وجود ندارد؛
  کاری که شد فقط چک دوباره در لحظه پرداخت است.
- Fulfillment خودکار (اتصال مستقیم به تلگرام برای ارسال واقعی گیفت/استارز)، Retry با Backoff، صف Notification،
  Refund خودکار روی شکست تحویل — این‌ها نیاز به یک Worker/Queue جدا (مثلاً BullMQ + Redis) دارند.
- Backup خودکار روزانه به S3/R2 — نیاز به حساب Object Storage و کلید API دارد که ندارم؛ ساده‌ترین راه فعلی:
  سرویس Litestream را روی همین SQLite فعال کنی (مستندات: litestream.io).
- Monitoring/Alerting واقعی (Sentry، Uptime robot) — نیاز به حساب در آن سرویس‌ها دارد.
- Migration به PostgreSQL/Redis، Dashboard آماری، Search/Filter/Pagination در پنل ادمین، Export CSV،
  Coupon/Referral/VIP، Feature Flags، Maintenance Mode، تست خودکار — همه این‌ها معماری تازه‌ای می‌خواهند،
  نه یک تغییر کوچک؛ اگر بخواهی، هرکدام را جدا و کامل می‌سازیم.
- package-lock.json — چون اینجا اینترنت ندارم نمی‌توانم npm install واقعی اجرا کنم تا لاک‌فایل بسازد؛
  اولین باری که خودت npm install را اجرا کنی (روی Render/Railway یا لوکال)، این فایل خودش ساخته می‌شود،
  فقط آن را هم به ریپو اضافه کن.

--- این دور: پیشرفت واقعی روی موارد بزرگ لیست (بدون نیاز به Postgres/Redis/S3) ---
- Order State Machine واقعی: paid → fulfilling → delivered، با مسیرهای failed و refunded،
  و enforcement سمت سرور (مثلاً delivered→processing یا refunded→delivered رد می‌شود).
- Idempotency تایید/رد/رفاند از قبل با بررسی وضعیت قبلی تضمین می‌شد؛ حالا روی همه‌ی state transitionها
  یکسان و متمرکز پیاده شده (تابع orderTransition).
- Price Lock با انقضای واقعی: هر آیتم سبد ۱۰ دقیقه اعتبار دارد؛ اگر منقضی شود، Checkout آن را رد می‌کند
  و پیام می‌دهد دوباره اضافه کن (نه اینکه با قیمت قدیمی حساب کند).
- Rate Provider metadata: منبع نرخ دلار، تعداد خطای پی‌درپی، و منبع قیمت استارز (دستی/تلگرام) در پنل ادمین دیده می‌شود.
- Telegram API Retry با Exponential Backoff + احترام به retry_after وقتی تلگرام کد 429 برمی‌گرداند.
- Notification Queue واقعی: پیام‌ها به‌جای fire-and-forget در جدول notif_jobs صف می‌شوند و با backoff تا ۵ بار
  دوباره تلاش می‌شوند؛ اگر باز هم شکست خورد، به بقیه ادمین‌ها اطلاع می‌دهد.
- Maintenance Mode و Feature Flags (گیفت/استارز/شارژ) از پنل ادمین قابل خاموش‌روشن‌کردن.
- Dashboard آماری (فروش امروز/هفته/ماه، برگشتی‌ها، صف‌های در انتظار، سلامت نرخ).
- Search + Pagination واقعی روی لیست سفارش‌ها و شارژها در پنل ادمین (limit همیشه بین ۱ تا ۱۰۰ کلمپ می‌شود).
- خروجی CSV برای سفارش‌ها/شارژها/لجر.
- Audit Log حالا IP و User-Agent هر اقدام ادمین را هم ثبت می‌کند؛ endpoint /api/admin/audit برای دیدنش.
- User Management پایه: مسدودکردن کاربر (blocked)، یادداشت روی کاربر، دیدن تاریخچه سفارش/شارژ هرکاربر
  (/api/admin/users/:id).
- هشدار ضدتقلب ساده: اگر یک کاربر بیش از ۱۰ درخواست شارژ در ۲۴ ساعت بزند، به ادمین‌ها پیام هشدار می‌رود
  (فقط هشدار، مسدود نمی‌کند — تصمیم نهایی دست خودت است).
- Cancel روی درخواست شارژ باز، از طرف خودِ کاربر.

--- هنوز واقعاً نیاز به زیرساخت بیرونی دارند (نه کمبود تلاش، بلکه نیاز به حساب/سرویس واقعی) ---
- RBAC چندسطحی: الان همه‌ی ADMIN_IDS یک سطح دسترسی کامل دارند؛ تفکیک Super/Finance/Support نیاز به
  یک جدول roles و بازطراحی همه‌ی middleware ادمین دارد — قابل ساخت است، فقط این دور وقتش نشد.
- Inventory Reservation واقعی برای گیفت: تلگرام API رسمی برای "رزرو یک گیفت مشخص برای یک کاربر" ندارد،
  چون خودِ فروش گیفت از طرف ربات به کاربر دیگر امکان‌پذیر نیست؛ این یک محدودیت پلتفرم تلگرام است، نه پروژه ما.
- Backup خودکار به S3/R2، Monitoring واقعی (Sentry/UptimeRobot)، Redis، PostgreSQL: نیاز به حساب و کلید
  در آن سرویس‌ها دارند که من ندارم و نمی‌توانم بسازم؛ در پیام‌های قبلی گفتم چطور خودت وصلشان کنی (مثلاً Litestream).
- تست خودکار (Jest/Vitest) و اجرای End-to-End واقعی روی یک بات زنده: نوشتن تست ممکن است، ولی اجرا و دیدن
  نتیجه‌ی سبز/قرمز نیاز به یک محیط اجرا با اینترنت واقعی و بات واقعی دارد که اینجا ندارم.
- package-lock.json و npm audit: نیاز به npm install واقعی با اینترنت دارند.
- SRI برای اسکریپت‌های CDN (lottie/telegram-web-app): محاسبه‌ی هش صحیح نیاز به دانلود واقعی فایل دارد؛
  اینجا نمی‌توانم. اگر خواستی، بعد از دیپلوی یک بار خودت با curl+openssl هش را بگیر تا اضافه‌اش کنم.
